# Axiom — Decision Log (Phase 1, Step 8)

Append-only. Newest entries go at the bottom with date + reason. Never rewrite past entries; supersede by reference.

| ID | Date | Decision | Reason |
|---|---|---|---|
| D-001 | 2026-10-17 | Modular monolith, one codebase, worker as separate process | Clear module boundaries without distributed-system failure modes; extract services later only on measured need |
| D-002 | 2026-10-17 | Celery + Redis for background tasks; PostgreSQL is source of truth | Dedicated task lifecycle; Redis is transport only, never authoritative state |
| D-003 | 2026-10-17 | Composite FK `(id, workspace_id)` + `UNIQUE(id, workspace_id)` on parent tables | Cross-workspace chunk/history attach impossible at the DB level, not just app code |
| D-004 | 2026-10-17 | State-based sweeper over transactional outbox for v0.1 | Sweeper closes all three crash windows (save-but-not-queued, worker death, broker loss); outbox closes only the first. Outbox trigger documented in `05-job-contract.md` |
| D-005 | 2026-10-17 | Exact vector search first; no ANN index in v0.1 | No measured scale problem yet; HNSW only if exact search is measured too slow (Phase 6) with filtered-recall check |
| D-006 | 2026-10-23 | Upload dedup is workspace-scoped SHA-256 and advisory (non-unique). It matches any status, preferring `indexed` > `queued`/`processing`/`retrying` > `uploaded` > `failed`; default returns the existing document, `allow_duplicate=true` creates a new one | Idempotent retries and no duplicate storage/processing; intentional re-uploads stay possible; cross-workspace dedup would leak existence; a unique constraint would block legitimate re-uploads |
| D-007 | 2026-10-23 | A duplicate upload answers `200` with the existing document; a new upload answers `202`; the existing document's metadata is unchanged | The status code describes whether new work was accepted. A duplicate is a successful lookup, not a new processing job |
| D-008 | 2026-10-23 | Introduce the `FileStorage` port and `LocalFileStorage`; storage I/O failures map to `503 DEPENDENCY_UNAVAILABLE` | Decouples ingestion from disk and allows an object store later. A valid upload that cannot be stored is not a `400 VALIDATION_ERROR` |
| D-009 | 2026-10-23 | Phase 3 keeps the single-commit `queued` handoff. The durable `uploaded` state, broker publish, and sweeper remain Phase 4 | Avoids a state no component can recover yet; Phase 4 owns the queue and the recovery path |
| D-010 | 2026-10-23 | Local Docker storage is a bind mount (`./backend/storage` → `/srv/backend/storage`) shared by `api` and `worker`; `storage/` is excluded from the build context | The worker must read the same bytes, and a host-run API must share the directory. Object storage is deferred until the local backend is proven |
| D-011 | 2026-10-23 | Phase 3 requires no Alembic migration; the existing `documents.checksum` column and `(workspace_id, checksum)` index carry dedup | A schema change would mean the Phase 1 schema was insufficient. Keeping the phase migration-free proves the original design and avoids a needless production migration |
| D-012 | 2026-10-23 | Ingestion and retrieval depend on the `FileStorage` port (`save`/`read`/`delete`/`exists`/`size`); `LocalFileStorage` is the only Phase 3 adapter. Keys are server-generated POSIX paths (`uploads/{document_id}/original.pdf`); the user filename is display metadata only | Keeps routes and the worker backend-neutral, makes path traversal structurally impossible, and lets an object store be added without changing the API |
| D-013 | 2026-10-23 | Operationalise D-006: workspace-scoped SHA-256 dedup is advisory and non-unique. It matches any status, preferring `indexed` > `queued`/`processing`/`retrying` > `uploaded` > `failed`; a duplicate returns the existing row unchanged, and `allow_duplicate=true` creates a new one | Idempotent retries and no duplicate storage/processing without blocking intentional re-uploads; cross-workspace matching would leak existence, and a unique constraint would create a conflict path the API does not need |
| D-014 | 2026-10-23 | Upload ordering is validate → checksum/dedup → `storage.save` → insert `queued` row → commit. A failed DB write rolls back and best-effort deletes the new object. Delete flushes the row delete, removes the object, then commits; a storage outage rolls the row deletion back, and a missing object is idempotent | A committed row must never point at bytes that were not durable. Ordering minimizes the dangerous window; compensation handles exceptions, not process death, and delete retries remain safe |
| D-015 | 2026-10-23 | Extend D-008's error mapping: storage I/O failures are `503 DEPENDENCY_UNAVAILABLE` (`retryable: true`); a missing object on download is `409 INVALID_STATE`; a missing object on delete is success; invalid keys/programming errors are `500` | The caller did not cause a dependency outage, so it must be retryable; a missing object is a state conflict, not a validation error; programming errors must not be presented as client semantics |
| D-016 | 2026-10-27 | Keep Phase 3's single-commit `queued` handoff and publish after the commit as a best effort; recover a failed publish through the sweeper's `queued` rule. Keep `uploaded` and its sweeper rule as a supported recovery state, but do not produce it from the current API | Avoids a save/enqueue split that no current component needs while preserving the Phase 1 recovery model; the committed row is durable even when Redis is down, and the sweeper closes the publish window. Supersedes D-009 only in that Phase 4 does not produce `uploaded`; the broker publish and sweeper parts of D-009 are implemented |
| D-017 | 2026-10-25 | `documents.process` carries only `document_id`; the claim resolves `workspace_id` from the row and repeats it in the UPDATE | The database row is the authority for workspace scope; a message cannot drift from it, and a forged id cannot select another workspace |
| D-018 | 2026-10-25 | `processing_attempts` increments only on a worker claim. Manual retry sets `failed → queued` without incrementing it; the next claim consumes the attempt. The claim enforces `attempts < MAX_PROCESSING_ATTEMPTS` (5) | The counter must mean "attempts a worker started", not "times a user clicked retry"; otherwise a user can bypass the failure budget before any work runs. A retry at the cap can be queued but cannot be claimed, and the sweeper fails it as `ATTEMPTS_EXHAUSTED` |
| D-019 | 2026-10-27 | Classify every processor failure on two axes: `transient` (automatic retry may help) and `retryable` (manual retry may help). Persist the latter as `documents.retryable`; cap exhaustion and permanent-final failures set it false | Separates "try again automatically" from "an operator can repair this"; a permission or missing-file condition is fixable but not transient, while a corrupt file is neither. Only `safe_message` is persisted or shown to clients |
| D-020 | 2026-10-27 | Publish a fresh task with a countdown after a transient failure commits; never use `self.retry()`. Configure a result backend but ignore results (`task_ignore_result=True`) | Celery's retry state must not become the source of truth; if the publish is lost, the sweeper can republish from `retrying`. The explicit result backend prevents Celery from silently falling back to another transport while the lifecycle continues to read only PostgreSQL |
| D-021 | 2026-10-27 | Guard the commit with `status IN ('processing','retrying') AND processing_attempts = :claimed`, and replace the chunk set in the same transaction. Zero-row document update → rollback; duplicate `(document_id, chunk_index)` → `CHUNK_CONFLICT` rollback | Status alone cannot distinguish the current worker from a stale worker that woke after a sweep. The attempt number is the fencing token; the single transaction ensures no partial new chunk set is ever visible |
| D-022 | 2026-10-27 | Use a state-based sweeper for `uploaded`, `queued`, `retrying`, and `processing`: commit transitions first, publish second, touch `updated_at` only after a successful publish, and serialize sweeps with a session-level PostgreSQL advisory lock | Closes the broker-loss, failed-publish, and worker-death windows without an outbox or a second source of truth. Publish-after-commit makes a crash safe; the timestamp marker prevents a failed publish from being treated as recovered; the lock keeps multiple Beat instances from racing |
| D-023 | 2026-10-27 | Split Redis into DB 0 (login rate limiting), DB 1 (Celery broker), and DB 2 (Celery result backend). Enforce `soft limit < hard limit < visibility timeout` and `processing stale > hard limit` at startup | Logical separation keeps the rate limiter from deleting or evicting task keys. The ordering makes a live task impossible to redeliver or sweep while it is still running; misconfiguration is a startup failure, not a production incident |
| D-024 | 2026-10-27 | Ship an integrity-only processor in Phase 4: verify the stored bytes and return zero chunks. `indexed` means the lifecycle completed, not that text/embeddings exist. Phase 5 replaces `get_processor()` and backfills the zero-chunk indexed set | Proves claim, commit, retry, and recovery end to end without coupling the milestone to extraction or embedding choices. The processor port is the replacement seam; the backfill must handle the attempt cap and `UNIQUE(document_id, attempt_no)` explicitly rather than silently resetting counters |
